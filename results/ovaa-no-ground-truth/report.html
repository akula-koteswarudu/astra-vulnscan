L01 · Exported component launches attacker-supplied Intent (intent redirection)

CWE-926 MASVS-PLATFORM
Look for
  • Exported component reads an Intent parcelable extra and passes it to startActivity
  • Implicit-intent result passed back unchanged via setResult(resultCode, data)
  • No check of target component or grant flags on the nested intent
Why The nested intent runs with the app's identity, reaching non-exported components or granting URI permissions on private providers. Reflecting a foreign result passes grants through to the caller.
Not a finding when
  • Nested intent's component is fixed and flags are cleared before launch
  • Component is not exported and only receives intents from trusted callers

L02 · FileProvider paths expose root or private storage

CWE-552 MASVS-PLATFORM
Look for
  • provider_paths XML has <root-path> or path="/" or "."
  • FileProvider has grantUriPermissions="true"
  • A redirection or result-reflection primitive can grant its URIs
Why A broad path mapping lets any granted content URI address any file the app can read, including private data. Combined with intent redirection, the attacker obtains the grant.
Not a finding when
  • Paths limited to a dedicated shared subdirectory holding no sensitive files
  • No code path lets untrusted callers obtain grants

L03 · Exported provider path traversal with file access

CWE-22 MASVS-PLATFORM
Look for
  • Exported provider without permission overrides openFile
  • File built from Uri.getLastPathSegment or getPath without canonicalization
  • Open mode permits write or create
Why URL-decoded ../ in the URI escapes the intended directory. Any app can read or overwrite files the victim can access, including private data.
Not a finding when
  • Provider protected by signature permission or not exported
  • Canonical path verified to be under an allowed base directory

L04 · Exported service writes to caller-chosen file path

CWE-73 MASVS-PLATFORM
Look for
  • Exported component takes file path string from intent extra
  • Component writes logs or data to that path with its own privileges
  • No permission or path validation
Why Caller controls the destination, so it can overwrite private app files or direct sensitive output to a location it can read.
Not a finding when
  • Component not exported or guarded by signature permission
  • Path forced into an app-controlled directory after canonicalization
File out = new File(intent.getStringExtra(<extraKey>)); write(out, <data>);

L05 · Weak <name> URL validation before WebView load

CWE-601 MASVS-PLATFORM
Look for
  • Host check uses endsWith or contains without a leading dot
  • Browsable <name> parameter passed to WebView.loadUrl
  • Scheme not restricted to https
Why Look-alike domains pass the check, so attacker pages load in a privileged WebView, exposing JS and file-access settings.
Not a finding when
  • Exact host equality against an allowlist with https enforced
  • WebView has JS and file access disabled and no bridges
if (uri.getHost().endsWith(<domain>)) webView.loadUrl(uri.toString());

L06 · Insecure WebView settings with intent-controlled URL

CWE-749 MASVS-PLATFORM
Look for
  • JavaScript enabled together with file-URL access flags
  • URL read from intent extra or <name>
  • file: scheme not rejected
Why A file: page can run script and read other local files, including private app data, then exfiltrate them.
Not a finding when
  • Only fixed trusted content is loaded, never intent input
  • File-access flags are false and scheme is restricted to https

L07 · <Class> parameter overwrites trusted endpoint setting

CWE-345 MASVS-AUTH
Look for
  • Browsable <name> persists a URL parameter into config or prefs
  • Stored value later used as a credentials-submission endpoint
  • No allowlist or user confirmation
Why A crafted link redirects subsequent authenticated requests to an attacker server, leaking credentials.
Not a finding when
  • URL validated against a fixed allowlist of hosts
  • Setting is only available in non-release builds

L08 · Dynamic code loading from untrusted location or package

CWE-94 MASVS-CODE
Look for
  • DexClassLoader path on external storage or world-writable directory
  • createPackageContext with CONTEXT_INCLUDE_CODE chosen by package name prefix
  • No signature or hash verification before loading
Why Another app can plant a file or install a matching package, so its code runs in this app's process and with its permissions.
Not a finding when
  • Code is signature-verified or loaded from app-private storage
  • Package must match a pinned signing certificate
new DexClassLoader(<externalPath>, <optDir>, null, getClassLoader()).loadClass(<name>);

L09 · Unsafe deserialization with side effects or arbitrary classes

CWE-502 MASVS-CODE
Look for
  • readObject performs file deletion or other actions using stream data
  • Parcel constructor reads class name then Class.forName and fromJson
  • Serializable or Parcelable extra read from an exported component
Why Attacker-crafted extras trigger the side effects or instantiate arbitrary classes during unparcelling, giving file deletion or gadget execution.
Not a finding when
  • Class never reachable from untrusted input
  • Class name checked against a fixed allowlist

L10 · Credentials or tokens sent over cleartext HTTP

CWE-319 MASVS-NETWORK
Look for
  • http:// base URL used for <name> or token requests
  • Token placed in a query string
  • No network security config blocking cleartext
Why A network attacker can read or modify traffic and capture credentials or tokens.
Not a finding when
  • Non-sensitive public content only
  • Cleartext blocked by config and URL is https at runtime
new Retrofit.Builder().baseUrl("http://<host>/")

L11 · Sensitive data in implicit broadcast or implicit intent

CWE-927 MASVS-PLATFORM
Look for
  • sendBroadcast with credential extras and no receiver permission
  • Implicit intent carries token or URL data
  • No setPackage or component pinning
Why Any app can register a matching receiver or activity and capture the secrets.
Not a finding when
  • Explicit intent or setPackage to own app
  • Broadcast guarded by a signature permission

L12 · Secrets stored or logged in plaintext

CWE-312 MASVS-STORAGE
Look for
  • Log calls on objects whose toString contains password or token
  • Password saved to SharedPreferences without encryption
  • Log dumped to files by a service
Why Other apps with log access, backups or device access can read the secrets; logs may be dumped to readable files.
Not a finding when
  • Value is non-sensitive or redacted
  • Stored via Keystore-backed encryption

L13 · Hardcoded keys and weak cipher modes

CWE-321 MASVS-CRYPTO
Look for
  • SecretKeySpec built from a string constant
  • Cipher.getInstance("<String>") with no mode
  • ECB mode, or static IV
Why Constant keys can be extracted from the APK to decrypt any protected data. ECB leaks patterns and offers no integrity.
Not a finding when
  • Key is generated at runtime in Android Keystore
  • Constant is unrelated to protecting sensitive data
new SecretKeySpec(<CONST>.getBytes(), "<String>"); Cipher.getInstance("<String>");

L14 · Debuggable build with backup enabled

CWE-1188 MASVS-RESILIENCE
Look for
  • android:debuggable="true" in release manifest
  • android:allowBackup="true" without backup rules
  • App stores sensitive data in private storage
Why Debugger, run-as or adb backup lets someone with device access extract private data and tamper with app execution.
Not a finding when
  • Debug-only build variant not shipped
  • Backup rules exclude sensitive files

  • Dev or test endpoint credentials
Why Anyone can unpack the APK and read the credentials, possibly gaining access to backend or dev systems.
Not a finding when

  • Value is a public non-secret identifier

8. Limitations

  • The lift is in-sample: lessons are distilled from the same app the student is rescanned on. One app cannot show that the lessons generalise (cross-app transfer is the partial answer).
  • Contamination: the evaluation app and its vulnerability list are public; the models may have memorised them.
  • Some ingest features (dependency inventory, cloud-identifier patterns) were added after reading the ground-truth list; they are generic, but not chosen blind.
  • Prompts were developed on this app (versions and scores are recorded in section 8).
  • Ground-truth enrichment is the author's own labelling (mitigated: written and committed before any scan, README-only headline, robustness check).
  • Some items are only partly visible statically (server-side cloud configuration; known-vulnerable components rely on the model's advisory knowledge).
  • The teacher's temperature cannot be set (Claude Sonnet 5.5 rejects non-default sampling); LLM output varies between runs; small N; no significance test.
  • Teacher refusals can reduce coverage (counted; the model that answered is recorded when a fallback was used).
  • Teacher and student may scan different units because of different budgets; the student's free tier (1,000 output tokens per minute) forces small units, and units whose answer does not fit are re-planned into smaller ones.
  • The judge is an LLM; the hand audit measures its agreement with the author, it does not remove bias.
  • One-to-one matching is conservative.
  • Unmatched findings are not automatically false positives (the reference list may be incomplete).
  • Teacher-as-reference (apps without ground truth) inherits the teacher's misses and mistakes and is circular with the lessons.
  • Decompilation is lossy (jadx failures are counted); the smali fallback is not built in v0.1.
  • Obfuscated apps: first-party code is derived from the manifest, but library detection is not fingerprint-based.
  • Native code, assets and split APKs / app bundles are not analysed.
  • Text-based one-hop graph: reflection, framework callbacks and string-action intents are missed; oversized files are skipped; no hub/skeleton handling in v0.1.
  • strings.xml filtering can miss innocently named, low-entropy secrets.
  • Prompt injection via app code or strings can still influence the model.
  • Model confidence is uncalibrated (used for ranking only).
  • The sanitiser is lexical plus a similarity check; paraphrased references can pass.
  • Lessons cover only the vulnerability classes the teacher found in the source app.
  • Line numbers refer to decompiled code.
  • Static only: runtime-only issues are out of scope (see the dynamic-analysis write-up).
